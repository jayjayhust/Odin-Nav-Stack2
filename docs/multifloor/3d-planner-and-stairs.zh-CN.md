# 3D 规划器移植与楼梯步态接入

本文记录"选项 2"（把 `jie_3d_nav` 的 `octo_planner` 移植成 ROS1 全局规划器）与"楼梯语义识别 + 步态切换"这两项的落地方式、边界和验证顺序。

---

## 1. 先明确移植的是什么、不是什么

`octo_planner` 的 3D 是**规划空间的 3D**，不是**运动空间的 3D**。证据在它自己的参数和控制器里：

| 证据 | 含义 |
| --- | --- |
| `tracking_point_reached_xy_tolerance: 0.40` | 到达判定只看 XY |
| `goal_position_tolerance: 0.1` / `goal_yaw_tolerance: 0.2` | 目标只有位置与偏航 |
| `d1_controller` 为纯 P 控制 + 横移 + final yaw + deadband | 输出是平面速度指令，不跟踪 z / pitch / roll |
| D1 为轮式底盘 | 物理上不能爬楼梯 |

所以移植后它提供：

- **3D 通行性判定**：`require_ground_support` + `ground_support_xy_radius_cells` 检查脚下是否有支撑面，能排除"桌面下方、悬挑、楼梯井空洞"这类 2D 投影会误判为可通行的区域；
- **单层内更安全的全局路径**：预阻塞半径 + 机器人半径，比 2D 栅格膨胀更少穿桌腿；
- **跨层拓扑**（仅在单张 3D 图成立时）：A\* 会自己绕到楼梯口。

它**不提供**：

- 楼梯运动（需要宇树运动控制层的爬楼步态）；
- 楼梯间定位（Odin1 掠射角点云退化）；
- 实时避障（`jie_3d_nav` 没有，本方案保留 ONS2 的 NeuPAN 做局部避障）。

## 2. 三个新组件

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| `octo_planner_ros1` | `ros_ws/src/octo_planner_ros1` | 3D 体素地图 + 3D A\*，暴露与 `map_planner` **完全相同的** `nav_interfaces/PlanPath` 服务 |
| `stair_gait` | `ros_ws/src/stair_gait` | 楼梯语义识别（up / down / flat + 踏步高度）+ Go2 爬楼步态切换闸门 |
| `stairs_gait_hook.sh` | `scripts/transition/` | 把上面两者编排成 `FLOOR_TRANSIT` 的 `autonomous` hook |

`mission_manager` **一行都不用改**：它只消费 `plan_service` 指向的 `nav_interfaces/PlanPath`。

## 3. 3D 规划器怎么接

### 3.1 与 2D 规划器并存，不替换

`robots/go2/robot.yaml` 里有 `global_planner: map_planner`，`map_planner.cpp` 用 `service_name` 参数发布服务。因此切换只需要改服务名：

```yaml
# 2D（默认，现状）
global_planner: "map_planner"

# 3D（单层内 3D 通行性判定）
global_planner: "octo_planner_ros1"
```

或直接给 `mission_manager` 的 `plan_service` 参数：

```bash
roslaunch mission_manager mission_manager.launch \
  plan_service:=/map_planner/plan
```

> 两个节点**不能同时**占用同一个服务名。启动 3D 规划器时，`go2.launch` 里请用 `enable_map_server:=0` 关掉 2D 的 `map_server`，或把其中一个的 `service_name` 改成 `/octo_planner/plan`。

### 3.2 参数与语义对齐

`config/octo_planner.yaml` 的参数名刻意与 `jie_3d_nav` 保持一致，便于对照调参：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `resolution` | 0.10 | 体素边长 |
| `robot_radius` | 0.25 | XY 膨胀半径，`ceil(0.25/0.10)=3` 格 |
| `inflation_z_cells` | 2 | Z 方向膨胀 |
| `max_iterations` | 500000 | A\* 展开上限，超时返回失败而不是拖死服务 |
| `require_ground_support` | true | 每步检查脚下支撑 |
| `ground_support_xy_radius_cells` | 1 | 支撑检查的 XY 窗口 |
| `snap_search_radius_cells` | 12 | 起终点吸附到最近可通行体素 |
| `max_step_z_cells` | 3 | 单次展开的最大 z 跳变，防止顺着未观测的井道"飞"到别的层 |
| `z_bias` | 0.0 | 偏离目标 z 平面的额外代价，用于偏好当前层 |

### 3.3 地图来源

两种，二选一：

```bash
# A. 预建点云（可复现，推荐先跑通）
rosrun octo_planner_ros1 octo_planner_node _pcd_file:=/path/to/floor1.pcd

# B. 实时累积（跟随 Odin1）
roslaunch octo_planner_ros1 octo_planner.launch cloud_topic:=/odin1/cloud_slam
```

`/odin1/cloud_slam` 发布在**里程计系**，节点通过 TF 变换到 `map_frame` 后再入图；TF 不可用时降级为原始坐标并只告警一次。

### 3.4 已知限制

- 体素图**一旦建立就不再扩展**：第一帧点云的包围盒 + `grid_margin_m` 决定了可用范围，后续超出范围的点被丢弃。单层测试够用；如果是整栋楼单图，需要先离线合并点云再加载。
- `deinflate()` 每次规划前 O(n) 扫描一遍（千万格量级约 10–20 ms），换来的是不需要维护第二份地图。
- 3D 路径的 `z` 保留在 `nav_msgs/Path` 里，但下游（`mission_manager` / NeuPAN）只用 `x,y,yaw`。**这不是缺陷**，是这套跟踪器的能力边界。

## 4. 楼梯语义识别

`stair_gait` 的检测器不分割整段楼梯，只回答一个问题：**机器人正前方的地面是上台阶、下台阶还是平地，每级多高**。

### 4.1 为什么降维成一维剖面

正经的做法是语义分割：把整段楼梯从点云里切出来，拟合出跑段、平台、边界，输出一个几何模型。这条路在现场走不通，原因不在算法而在数据：

- 踏面相对于 Odin1 是**掠射角**。激光几乎平行于踏步表面入射，反射点稀疏且不稳定，一段 9 级的梯段常常只回来零星几条带；
- 楼梯是**分段不连续**的曲面。任何拟合都要求一整片连通面，而阶梯恰恰是 9 个互不连通的水平面加 9 个垂直面；
- 分割出来的几何，步态层也用不上——它不需要"这段楼梯长 2.7 m、坡度 32°"，它只需要"该不该切爬楼步态、切上行还是下行"。

所以检测器把问题降到一维：**沿 `base_link` 的 +x 方向，取一条高度剖面，看它是不是一级一级往上跳。** 这个降维带来一个很关键的性质——剖面是在机器人自身坐标系里取的，与 SLAM 是否建好了图、当前在第几层、2D costmap 有没有覆盖到这里，全都无关。4 层楼里的任何一层、任何一个梯段脚下，同一个检测器都同样工作。

### 4.2 五步，以及每一步为什么这么选

**(1) 圈 ROI 再分 bin。** ROI 是 `x ∈ [0.8, 3.2] m`、`|y| ≤ 0.6 m`、`z ∈ [-0.75, 0.6] m`，按 0.05 m 沿 x 分 bin。下界 0.8 是为了避开狗自己的身体和正前方的地面反光；上界 3.2 是"提前一级楼梯开始判断"的提前量；`y` 半宽 0.6 对应梯段 1.2 m 宽度的一半，让剖面走梯段正中；`z` 窗口把上方楼板、扶手、天花都排除在外。

**(2) 每个 bin 取最低点。** 这一条是整个方法的地基。一个 bin 里可能同时有：踏面、上一级踢面、梯井墙、门框、狗自己的腿、扶手的回波。其中**踏面永远是地面上最低的那层**。取最小值，天然滤掉上方的一切，不需要做任何分类。代价是它对**缺失**极其敏感：如果掠射角让这个 bin 根本没扫到踏面，只剩上方回波，那"最低点"就被高估，于是产生一个假的向下跳变。后面两步都是为这个代价兜底。

**(3) 3 点中值，不是均值。** 上一步的假跳变表现为单 bin 的尖锐孤点。均值会被这个孤点拉动（它参与求和），中值直接把它丢掉——只要左右两个 bin 正常，中间那个坏值就被替换掉。这就是选 3 而不是 5，选 median 而不是 mean 的原因：**已知噪声形态是稀疏孤点，中值是对症的那把刀。**

**(4) 扫相邻 bin 的高度跳变。** 这里刻意不用"拟合平面求斜率"。斜率的前提是连续面，而楼梯是分段不连续；跳变检测则直接对应物理事件——**一次跳变就是一个踢面**，而且跳变幅度本身就是要找的踢面高度，不需要从斜率反推。判据是三重的：

- 幅度落在 `[0.08, 0.30] m` 才算一次踏步。下界 0.08 滤掉踏面倾斜和地砖噪声，上界 0.30 把"一整层墙"和"跨层"排除。现场踢面 0.189 m，落在窗口正中。
- **跳出窗口时重置**。这一条比窗口本身更重要：遇到一个 0.6 m 的跳变，说明前面是墙或跨层，两段连续计数都要清零，不能让计数跨过墙去累加。
- 只统计**连续同向**的跳变。一次向上的跳变可能是门槛、地砖接缝、斜坡的起坡；连续两次同向，才基本排除这些偶发结构。

**(5) 时序确认。** 判出 `up` / `down` 之后不立即发布，要连续 `confirm_frames` 帧（默认 3，即 10 Hz 下 0.3 s）都是同一状态才认。状态一变就重置计数。这解决的是临界处的抖动：狗站在梯段最下面一级时，剖面可能这一帧看着像平地、下一帧看着像台阶。

### 4.3 两个"拒绝"比"判对"更重要

这套方法的价值有一半在它**不肯下结论**的时候：

- **踢面高度差异超过 `0.06 m` → 判 `unknown`**。真楼梯的踢面高度受施工公差约束，是一致的；如果扫出来的跳变一会儿 0.10 一会儿 0.26，那面前的大概率不是规整楼梯，而是斜坡上的杂物、破损台阶或不规则台阶。此时切爬楼步态比不切危险得多。
- **连续同向跳变不足 `min_steps`（2 次）→ 判 `flat`**。宁可当平地走过去，也不因为一脚门槛就抬腿。

整个设计取向是：**漏检的代价是狗停在楼梯前等人，误检的代价是狗在平地上摆出爬楼姿势甚至向上冲。** 这两种错误的代价不对称，所以阈值全部往保守的方向配。

### 4.4 输出与消费者

`/stair_gait/status`（`std_msgs/String`，latched，JSON）：

```json
{"state":"up","steps":3,"rise":0.168,"span":0.93,"confidence":0.75,
 "api_ids":{"gait":1011,"mode":1049},"actuation":false}
```

- `state`：`flat` / `up` / `down` / `unknown`；
- `steps` / `rise` / `span`：看到的级数、平均踢面、覆盖的 x 跨度——**只用于日志和诊断，不用于几何计算**；
- `confidence = min(1, steps/4)`：这是一个**饱和函数，不是概率**。它的含义是"看到了几级"，4 级以上不再增加信息量，所以封顶。不要把它当成把握程度来用。
- `api_ids` / `actuation` 带在消息里，是为了让日志一眼能看出"这次为什么没动腿"。

消费者有三个：`auto_switch`（节点自己切步态）、`mission_manager`（跨层任务的门控）、以及任何订阅它的外部工具（Foxglove、现场脚本）。消息用 JSON 而不是自定义 msg，就是为了让这些消费者都不需要编译新的消息定义。

### 4.5 它做不到什么

必须写清楚，因为这些正是它**只被用来触发、不被用来算几何**的原因：

- **掠射角导致 bin 缺地面点**：产生假跳变，中值滤波只能救回孤立的单 bin，救不回连续两三个 bin 的空洞；
- **玻璃栏板不产生回波**：ROI 边缘可能完全没有边界信息，检测器不知道梯段有多宽，也就无法判断狗是不是偏离了中线；
- **停车姿态**：`base_link` 抬头或低头时，整条剖面会倾斜，倾斜在剖面里长得和楼梯很像；
- **`|y| ≤ 0.6 m` 是假设**。狗没有停在梯段正中时，ROI 会框到栏杆或墙，把边界当成踏步。

结论是：**语义识别负责"该不该切步态"，不负责"我在梯段上的哪个位置"。** 后者要靠 8.6 节的中线约束在规划阶段解决，靠现场加挡边在感知阶段解决。

## 5. Go2 爬楼步态接口：查证结果

### 5.1 固件/ROS2 侧确实存在

宇树 Go2 ROS2 文档（`unitree-go2-robot.github.io`）明确列出：

| 接口 | 参数 | 取值 |
| --- | --- | --- |
| `/switch_gait`（`go2_interfaces/srv/SwitchGait`） | `int32 gait` | 0 IDLE / 1 TROT / 2 TROT_RUN_NING / **3 FORWARD_CLIMBING_MODE** / **4 REVERSE_CLIMBING_MODE** |
| `/mode`（`go2_interfaces/srv/Mode`） | `string mode` | 含 **`walkstair`**（"climb stairs in a walking pattern"）、`walkupright`、`freewalk` 等 |

Go1 的 `gaitType` 定义（3 = Stairs climbing）也印证了这套编号的谱系。

### 5.2 `unitree_sdk2` 的 C++ 头文件里没有

`include/unitree/robot/go2/sport/sport_api.hpp` 列出的 API ID 为 1001–1063、2041–2058，**不含 `SWITCHGAIT` 也不含 `WALKSTAIR`**；`sport_client.hpp` 的 `SportClient` 方法全集里同样没有。

这不是"接口不存在"，而是**没在这个公开头文件里注册**。宇树自己的教程（`serviceconsole.unitree.com` `#/help/030504`）讲"如何在 unitree_ros2 中添加接口"时也强调：**API ID 必须与 `unitree_sdk2` 中的定义一致，不能随意编造**。

### 5.3 本项目的处理方式

`stair_gait/include/stair_gait/ext_sport_client.h` 做了三件事：

1. 继承 `unitree::robot::go2::SportClient`；
2. 利用其 **protected** 的 `Call(apiId, param, data)` 与 `RegistApi(apiId)` 发任意 API；
3. 把 API ID 做成 ROS 参数 `switch_gait_api_id` / `mode_api_id`，**默认 -1 = 不调用**。

```cpp
int32_t SwitchGaitById(int32_t api_id, int32_t gait) {
  if (api_id < 0) return -1;
  RegistApi(api_id, 0);
  const std::string param = std::string("{\"gait\":") + std::to_string(gait) + "}";
  std::string data;
  return Call(api_id, param, data);
}
```

这样既没有编造 ID，也在接口存在时能真正调通。API ID 从你手上的 `unitree_ros2` 源码（`ros2_sport_client.h` 中 `ROBOT_SPORT_API_ID_SWITCHGAIT` / `WALKSTAIR` 常量）或宇树技术支持处取得后填入即可。

### 5.4 安全闸门

- `enable_actuation` 默认 **false**：所有服务直接返回 `success=false`，不碰机器人；
- `auto_switch` 默认 **false**：即使检测到楼梯也不自动切步态，必须由 hook 显式调用；
- 每个服务返回原始 `int32` 返回码，错误的 ID 会表现为非 0，而不是静默失效；
- `stairs_gait_hook.sh` 用 `trap` 保证异常退出时**先停车、再恢复 trot**。

## 6. 落地顺序（建议严格按此执行）

| 步 | 动作 | 通过标准 |
| --- | --- | --- |
| 1 | 只跑 3D 规划器，`pcd_file` 指向一层点云，用 `rosservice call /map_planner/plan` 打点 | 返回 `success=true`，`path.poses` 不穿墙、不悬空 |
| 2 | 把 `plan_service` 切到 3D，单层内跑一次完整任务 | 状态机正常，NeuPAN 仍在避障 |
| 3 | 只跑 `stair_gait`（`enable_actuation=false`），人走一遍楼梯看 `/stair_gait/status` | `up`/`down` 判定正确，踏步高度与实测一致 |
| 4 | 取得 API ID，`enable_actuation=true`，机器狗架空空跑（腿悬空）验证 `SwitchGait` 返回 0 | 三个服务返回码均为 0，机器人姿态按预期变化 |
| 5 | 楼梯口实地，`mode: manual` + 人工监护，跑 `stairs_gait_hook.sh` | 能上、能下、到层后重定位成功、端点校验通过 |
| 6 | 连续 20 次无失败后，才考虑去掉监护 | — |

**第 4 步不可跳过**。错误的 API ID 有可能落到别的 service 上，空跑是唯一安全的验证方式。

## 8. 离线仿真（不需要 ROS）

`test/planner_sim.cpp` 直接链接 `src/voxel_grid.cpp` 和 `src/astar3d.cpp`——这两个文件只依赖 STL，所以能在一台没有 ROS、没有 PCL 的机器上用 `g++` 单独编译，跑的是和机器上完全相同的一份规划代码。

```bash
cd ros_ws/src/octo_planner_ros1
g++ -std=c++14 -O2 -I include test/planner_sim.cpp \
    src/voxel_grid.cpp src/astar3d.cpp -o /tmp/planner_sim
/tmp/planner_sim > ../../../../docs/multifloor/sim/planner_sim_data.json
python3 test/build_sim_report.py     # 生成 docs/multifloor/sim/planner_sim.html
```

HTML 是自包含的（数据内嵌，无外部库、无服务器），打开后可以切换场景、拖时间轴回放 A\* 的展开过程和出图过程。三个视图分工如下：

- **俯视 X-Y**：平面走向、A\* 的扩散范围。
- **侧视 X-Z**：按目标所在 y 切 ±3 格看高度剖面，路径的每次抬腿都对应一级台阶。
- **3D 点云**：体素中心做透视投影，拖拽旋转、滚轮缩放、双击复位。没有面遮挡，所以不需要画家排序，深度只用来决定点的大小和透明度。视锥按包围盒自动拟合，任意角度都不会裁出画布。颜色按高度从冷蓝到暖黄，楼层和爬升方向一眼可辨。

**楼梯按真实梯井建模，不是开放式斜梯。** 梯井两侧（`y = 0.55` 与 `y = 3.05`）有贯穿全高 13.8 m 的墙，平台背后一道墙，只留两端平台作进出口。单梯段的 `stairs` 场景同样处理，两侧墙到 2.6 m。

**栏杆按"点云能不能扫到"来建模，这是这一节最要紧的一条。** 机器人靠 Odin1 的点云建图，而点云只返回**被激光打到过的表面**。楼梯两侧若只是一片敞开的踏面边缘，扫描返回的就只有踏面本身，梯边一个 occupied 格都不会有——`inflate` 无从生长，规划器看到的是"旁边什么都没有"，于是让机器人贴着边走，甚至走出去。多级楼梯上这就是摔下去。

所以每一级踏面前缘都立一根 **0.95 m 高的立柱**，两侧对称，柱间距等于踏面宽 0.30 m；沿坡度再铺三条连续线：踢脚板（踏面 +0.06 m）、中横杆（+0.45 m）、扶手（+0.95 m）。

真正起作用的只有立柱，原因是膨胀的机制：`inflate(rxy, 0, ...)` 只在 XY 平面扩散，z 方向不传导。0.95 m 高的扶手膨胀出来的 INFLATED 落在 0.95 m 那一层，而机器人走的是踏面层，管不着它。立柱从踏面第一格起就是连续的 occupied，所以每一级台阶都在梯边生成一条 0.25 m 宽的膨胀带。

效果可以直接从路径上量出来：上行跑的梯段横跨 `y ∈ [1.8, 3.0]`、中线 2.4，而路径实际只落在 **y ∈ [2.35, 2.55]**——两侧各 0.25 m 的膨胀带把机器人压在中线上，它没有贴边的余地。

这个改动不只是外观：楼梯一旦两侧封闭，A\* 的搜索空间立刻被约束在梯段内部，`multi_floor` 的 `expanded` 从 11499 降到 7423，少了 35%（这两个数字出自 3 层版本，扩到 4 层后同一对比较的绝对值都会变大，比例关系不变）。开放式楼梯意味着规划器可以"从侧面平移到某一级踏步上"，那在真实机器人上是踩空。

| 场景 | 构造 | 验证的语义 |
| --- | --- | --- |
| `office` | 8×6 m，两张悬空桌面 + 桌腿 | 能从桌面下方穿行，不是把整张桌子当墙 |
| `stairs` | 8 级（踏面 0.30 / 踢面 0.17）+ 上层平台 | 沿台阶逐级上升，不被踢面挡住 |
| `pit` | 地面 1×1 m 空洞，目标在洞中心 | 不把空洞当成可站立面，目标吸附到洞边 |
| `wall_start` | 起点距墙 0.15 m，整个人站在膨胀带里 | 仍能出图，不会一次展开就放弃 |
| `desk_barrier` | 桌面横跨整条走廊，只在桌下 0.75 m 留通道 | 2D 投影是死墙，3D 能穿过去 |
| `multi_floor` | 4 层办公楼，层高 3.4 m，双跑楼梯每层两段各 9 级（踢面 0.189 / 踏面 0.30）+ 端部 1.2 m 转弯平台，梯井贯通四层，起点 1 层、目标 4 层 | 跨 4 层出图：0 → 3.4 → 6.8 → 10.2 m，三次爬梯 |

七个场景共 17 条断言，当前全部通过（office expanded 1228 / stairs 559 / pit 97 / wall_start 1338 / desk_barrier 590 / multi_floor 15529 / multi_floor_glass 15768，单次规划 0.2–15 ms）。

`multi_floor` 的几何值得单独记一笔，因为它决定了这个场景到底在证明什么。

双跑楼梯（twin-flight stair）在平面上是一个 U 形：上行跑和下行跑**并排**，各占梯井的一半宽度（`y ∈ [1.8, 3.0]` 与 `y ∈ [0.6, 1.8]`），每跑 9 级升半层 1.7 m；跑到头是 1.2 m 深的**转弯平台**（`x ∈ [5.7, 6.9]`），人在平台上转 180° 再走另一跑。楼板在每个梯井位置开洞，洞从一层通到四层。

早先的版本把两跑叠在同一个 x、同一个 y 上，只靠 z 带区分——那其实是"直上直下的叠置楼梯"，没有平台，也没有转弯，人根本走不通。改成并排之后，路径在平面上呈现 U 形，转弯平台是必经节点。

这也说明 3D 规划器处理的不是"一张平面图加一个高度"，而是真正的四层体空间：它要靠 `groundBelow` 在每一列找到当前楼层的踏面，靠 `max_step_z_cells`（3 格 = 0.3 m）拒绝跨层跳跃，靠 `require_ground_support` 确认每级踏步下方确实有支撑。在这个场景里 A\* 展开 15529 个节点、出 313 点路径，耗时 14.4 ms——放在 Orin Nano 上按 5–10 倍余量估算，仍在单次规划百毫秒量级，可以接进 2 s 的周期重规划。

## 8.5 现场楼梯的感知缺口（按实拍复核后重做）

现场楼梯不是"竖条栅栏"，而是**夹胶玻璃栏板**：不锈钢立柱约 1.35 m 一根，玻璃板夹在立柱之间，顶部一根 φ50 圆管扶手，每跑的**外侧**是实墙。

这个结构对 3D 规划是**最坏的一种情况**，原因不在几何而在物理：

- 905 nm 激光对夹胶玻璃基本是**穿透**的，玻璃板在点云里几乎不贡献任何点；
- 能返回的只有立柱（1.35 m 间距）和圆管扶手；
- 扶手在 1.0 m 高，而膨胀只在 XY 平面扩散、**z 方向不传导**，所以扶手那个高度的 INFLATED 落在机器人永远到不了的高度。

于是两跑之间的那道分界线在感知里是**断的**：0.25 m 的膨胀带只能围着立柱画圈，圈与圈之间留出 0.85 m 的空档，A\* 直接从空档里穿过去。

这不是推测，把实拍几何填进仿真就复现了。同样一栋四层双跑楼梯，只改栏杆的建模方式，路径贴着梯边的程度完全不同（梯段边界在 `y = 1.80`，越过它就意味着踩空）：

| 栏杆建模 | 上行跑路径 y 范围 | 下行跑路径 y 范围 | 判断 |
| --- | --- | --- | --- |
| 每级踏面前缘一根立柱（0.30 m 间距） | 2.35 – 2.55 | 1.35 | 压在中线，安全 |
| 实拍：玻璃栏板 + 1.35 m 立柱 | 2.15 – 2.65 | **1.75 – 1.95** | 越过边界 15 cm，**踩空** |
| 实拍 + 6 cm 连续矮挡条 | 1.95 – 2.55 | 1.65 – 1.75 | **更糟**：挡条被当成可站立面 |
| 实拍 + 22 cm 连续挡边 | 2.25 – 2.65 | 1.35 – 1.45 | 回到中线，安全 |

第二行和前两行的差别，就是"点云扫不扫得到"这一个变量的全部重量。

表里还有第五种情况没列，因为它改的不是建模而是规划器：**同一个无挡边、玻璃完全不可见的版本，加上 8.6 节的中线约束之后，梯段内平均偏离中线也是 0.06 m**，和装了挡边一样。这说明两件事可以分开修——感知缺口归挡边，入口对准归规划器。但两者不能互相替代，理由在 8.6.4 节。

**6 cm 那条为什么反而更糟。** `skip_standing_surfaces` 的判据是"正上方为 FREE 的 occupied 格可站立，不参与膨胀"。5 cm 只有一格高，顶上是空的，于是被判成"可站立面"——它既不膨胀，还给 A\* 提供了一条贴着梯边的窄道，路径反而更靠外。**矮于两格（0.2 m）的结构在现有判据下是负资产。**

**结论：现场加一道 ≥ 20 cm 的连续挡边。** 而不是指望算法去分辨 5 cm。玻璃栏板底座本来就需要收边，把这道收边做成 20 cm 高的金属踢脚（或干脆换成实体护栏底座），感知立刻连续，膨胀立刻闭合，规划器自己就会把机器人送回中线。这是整个项目里性价比最高的一次现场改造。

在那之前，**爬楼动作不要交给 3D 规划器**。`stair_gait` 的开环直行只跟踪梯段中线，不依赖侧向点云；规划器负责把它送到梯口、再从梯口接走。两者分工清楚了，玻璃栏板扫不到也不会变成事故。

### 8.5.1 挡边规格（给施工用的那张单子）

上面那张表的结果可以换算成四条验收条件。少一条，感知就还是断的：

| 项 | 要求 | 为什么 |
| --- | --- | --- |
| 高度 | **≥ 0.20 m，连续** | 低于 0.2 m（两格）会被 `skip_standing_surfaces` 判成可站立面，既不膨胀还给 A\* 开一条贴边窄道，比不装更糟（见 8.5 表里 6 cm 那行） |
| 连续性 | 沿每跑两侧**不得断口**，转弯平台要包住 | 断口处没有回波，膨胀带在断口断开，路径从断口穿出 |
| 位置 | 每跑的**内外两侧都装**，平台外侧同样 | 现场内测是玻璃栏板、外侧是实墙，实墙那侧本来就有回波；要补的恰恰是玻璃这一侧 |
| 材质 | 金属或混凝土，**不需要反光涂层** | 只要能被 905 nm 打到就有回波；玻璃的问题是不管怎么处理都会穿透 |

高度跟扶手不冲突：挡边在踏面上 0.20 m，φ50 扶手在 1.0 m，中间玻璃板照旧。挡边等于给玻璃栏板加了一道踢脚，本来也是收边需要的做法。

**别把挡边当成"帮规划器看清"的临时补丁。** 它真正解决的是三件事，缺一件都不算解决：实时点云能生成边界膨胀（局部规划器用）、语义识别能判断梯段宽度（`stair_gait` 用）、全局路径能知道梯段在哪（A\* 用）。

## 8.6 楼梯段的中线约束（为什么全局路径不能贴边走）

### 8.6.1 问题的真正形态

A\* 给出的贴边路径在数学上是**最优的**：`astar3d.cpp` 的代价只有步长加启发函数，最短就是最优。但它默认了一件在楼梯上不成立的事——**规划出来的路径会被闭环跟踪**。

实际上不会。跨层时 `stairs_gait_hook.sh` 干的是：

```
stop_motion                    # 连发 5 次零速
rosservice call /neupan/stop    # 局部规划器被显式停掉
rosservice call /stair_gait/enter_climb
12 秒内每 0.1 s 发一次 {linear.x: 0.25, linear.y: 0.0, angular.z: 0.0}
```

`linear.y` 是硬编码的 0。**这 12 秒里没有任何东西在纠正横向偏差**——局部规划器被停了，语义识别只给"上/下"不给横向位置，点云里的玻璃还是透明的。所以机器人在梯口那一刻的横向偏移，会原封不动走完整个梯段。

按 `robot_radius = 0.25` 算：路径中心距梯边 0.25 m，狗半宽约 0.15 m，狗体边缘距边界只剩 0.10 m。爬楼步态本身有横向摆动，一跑 2.7 m 走完，这点余量不够。

### 8.6.2 机制

`AStar3D::Params` 里加了一组 `Corridor`：

```cpp
struct Corridor {
  double x_min, x_max;   // 沿跑段的范围（米）
  double y_centre;       // 要走的那条中线
  double y_half;         // 生效的横向半宽
  double z_min, z_max;   // 生效的高度范围
  double weight;         // 每偏离 1 米加多少代价
};
```

`plan()` 里候选格算完步长代价之后，再按格子的世界坐标查一遍走廊：

```cpp
lateral += weight * fabs(wy - y_centre);   // 只在走廊盒子内累加
const float tentative = cur.g + step + zbias + lateral;
```

三个设计选择值得说清楚：

- **在搜索时加，不是事后平滑路径。** 事后平滑只能挪中间点，改不了"路径在梯口那一刻是否对准中线"。放进代价里，A\* 会在进入梯段之前就开始横移，让入口本身就是正的。
- **只在盒子内生效。** 走廊只覆盖每一跑的 x 范围，不覆盖转弯平台——平台本来就要转，硬拉中线反而不像人走路。平层完全不受影响。
- **是可加代价，不是硬约束。** 走廊里若找不到可行走格，规划器仍给路径（代价高）而不是直接失败。硬约束在现场只会变成"无解"，更难查。

### 8.6.3 实测

四层场景声明了 6 条走廊（3 个层间 × 上下两跑），`weight = 3.0`：

| 场景 | 梯段内平均偏离中线 | expanded | 耗时 |
| --- | --- | --- | --- |
| `multi_floor`（有 0.22 m 挡边） | 0.06 m | 15529 | 14.4 ms |
| `multi_floor_glass`（无挡边、玻璃不可见） | 0.06 m | 15768 | 14.0 ms |

两个版本都落在中线上。**这条最值得注意**：玻璃版连一个边界回波都没有，它照样走中线，因为走廊代价根本不看感知，它看的是声明。

代价是 `expanded` 从 13241 涨到 15529（+17%）——带惩罚的搜索要展开更多候选，才能证明"中线那条更便宜"。

### 8.6.4 这套机制的边界

**走廊是人工声明的，不是自动识别出来的。** `multi_floor` 里的 6 条写在 `buildMultiFloor()`，真机上应当从 `floors.yaml` 或地图元数据读。由此带来三个约束：

- 声明的中线和实际梯井对不上时，规划器会把路径拉到**错误的位置**，而且它不会自己发现——它不看感知，就没有纠正的机会；
- 换一栋楼、换一个梯井，走廊必须重配；
- 梯井几何改动（比如加挡边改变了净宽）之后，中线要复核。

所以走廊解决的只是**入口对准**，它假定梯段几何已知。真正的闭环仍然要靠挡边：挡边让实时点云有边界，局部规划器和语义识别才有东西可用。两层保险，不能拿一层替另一层。

### 8.6.5 还能往前走的一步

现在走廊的 z 范围按 `FL = 3.4` 硬分。更彻底的做法是让 `stair_gait` 的语义识别输出梯段宽度和横向位置，直接喂给规划器当走廊——那样换楼就不用重配。但 4.5 节说得很清楚，语义识别现在只给得出"上/下/平地"，给不出横向几何。这一步要等挡边装上、ROI 边缘有稳定回波之后才谈得上。

## 9. 仿真暴露的五个真实缺陷（已在代码里修掉）

### 9.1 Z 方向膨胀会吞掉脚下的站立格

`inflation_z_cells: 2` 的本意是防止机身擦到头顶的横梁。但在体素里，"地面"本身就是占一格高的 occupied，向上膨胀 0.2 m 正好把机器人站立的那一格变成 INFLATED —— 结果是地面和每一级踏步全部不可规划。

现在默认 `inflation_z_cells: 0`。头顶净空由 `clearance_cells` 保证：每插入一个表面点，就把它正上方 20 格（2 m）的 UNKNOWN 清成 FREE，这已经覆盖了机身高度。

### 9.2 XY 膨胀会吃掉下一级台阶的站立格（最关键的一条）

这一条只有真跑楼梯才暴露得出来。踏步升高 0.17 m ≈ 1.7 格，于是：

- 第 N 级踏步的表面占 `iz = 8`（0.51 m）；
- 第 N+1 级踏步的表面占 `iz = 9`（0.68 m），机器人站在第 N 级时正好也是 `iz = 9`。

第 N+1 级表面的 `robot_radius`（0.25 m = 3 格）XY 膨胀落回同一层 `iz = 9`，把第 N 级的站立格整片变成 INFLATED。搜索于是停在第三级，`expanded=684`、`no path found`。

修法不是把半径调小（调小就失去避障意义），而是给 `inflate` 加 `skip_standing_surfaces`：**正上方是 FREE 的 occupied 格是"可站立面"（地面、踏步、桌面），不参与膨胀；只有竖直结构（墙、桌腿、护栏）才膨胀**。这一条同时让单层走廊不再因为地面膨胀而损失 0.25 m 通行宽度。

### 9.3 支撑容差让机器人站到梯段边缘之外，还能竖直飞升

`ground_support_xy_radius_cells = 1` 的支撑判定是"`iz-1` 层、xy 半径 1 格内任意一格是 occupied 就算有支撑"。它在单层走廊里是必要的宽容——点云只要漏一格，机器人就没法站；但在楼梯上它变成了漏洞：

梯段边界在 `y = 1.80`，玻璃立柱立在 `y = 1.76` 和 `1.84`。于是 `y = 1.65` 这一列**本身没有踏面**，却因为旁边 `y = 1.75` 的立柱被判为可站。A\* 顺着这条"虚边"往前走，还出现了 3 处**纯竖直上升**——相邻两点的 x、y 完全不变，z 一次抬高 1.6 m（8 步 × 0.2 m，每步都靠横向相邻格拿到支撑）。侧视图上一看就是"没踩楼梯、凭空飞上去"。

这条只有把支撑判定从 1 格改成 **0 格**（正下方那一格必须自己就是 occupied）才收得住：

| 支撑半径 | `multi_floor_glass` 路径 | 纯竖直相邻步 | 每段爬梯点数 |
| --- | --- | --- | --- |
| 1 格 | 158 | **3** | 12 / 11 / 13（跳段） |
| 0 格 | 189 | **0** | 22 / 22 / 22（走满） |

代价是真实点云稀疏时更容易判成"不可站"。降级顺序应该是先靠 `snap_search_radius_cells` 吸附、再靠提高地面点密度，而不是把这个容差放宽——放宽之后在楼梯上付出的是踩空的代价。

### 9.4 起点落在膨胀带内时 A\* 一次都扩展不出去

机器人贴墙站（距墙 0.15 m）时，起点本身以及周围 0.3 m 全是 INFLATED。旧代码的端点判定是"INFLATED 也接受"，但邻居严格要求 `kFree`，于是 `expanded=1` 直接放弃。

改为**端点优先吸附到最近的 FREE 格**（`snap_search_radius_cells=12`，即 1.2 m 内找），实在找不到才退回 INFLATED。这样贴墙起步也能出图，代价是路径起点会平移 0.2–0.3 m —— 对 `mission_manager` 无影响，因为它只取路径做跟踪参考。

### 9.5 场景构建本身的两个坑（不是算法问题）

- `addWallY(x, ...)` 建的是**垂直于 x 轴**的墙，`addWallX(y, ...)` 建的才是沿 x 延伸的侧墙。楼梯场景一开始把侧墙写成了 `addWallY(0.0/2.6, ...)`，等于在梯段中间竖了两道横墙，把楼梯切断。
- 浮点误差：`(2.6 + 0.3) / 0.1 = 28.999…`，`floor` 之后落到 `ix = 28`，与踏步列重叠。场景里所有落在网格边界上的坐标都要留出余量，或者干脆用半格偏移。

## 10. 仿真的结论边界

仿真证明的是"几何上可规划"：3D A\* 能找到一条从一层走到另一层的、贴着踏步逐级上升的路径。它**不证明**机器人能执行这条路径——真正的爬楼动作仍然要靠 `stair_gait` 把步态切到 `FORWARD_CLIMBING_MODE`，由宇树的运动控制层完成。规划器给的是"往哪走、抬多高"，步态给的是"腿怎么动"，两者缺一不可。

## 11. 点云环境的实时导航与避障闭环仿真

第 8、9 章那个仿真器（`test/planner_sim.cpp`）回答的是"几何上能不能规划"：给定一张已经建好的体素图，A\* 能不能从一层走到另一层。它没有感知、没有闭环、没有碰撞——路径对不对只靠人工看图和断言。

第 11 章这套（`test/nav_sim.cpp`）回答的是另一个问题：**机器狗拿着真实的稀疏点云，一边跑一边建图，会不会撞**。三个环节缺一不可：

```
射线扫描（带噪声/丢点/FOV 盲区）
   → 体素占据 + 膨胀
   → 3D A* 全局路径（每 1.5 s 或偏离 0.45 m 重规划）
   → DWA 采样局部避障（每 0.1 s）
   → 真值 OBB 碰撞判定（与感知无关，只用于打分）
```

真值障碍和感知点云是两套独立数据：碰撞判定只看真值几何，不看机器人自己以为的地图。这样"感知漏了 → 撞了"才会被如实记成 `collided`，而不是被机器人自己的地图自我验证。

四场：三场平地（3D 通行性、跑起来才发现、窄通道对向避让），一场跨楼层（双层楼梯芯）。跨楼层那场是装置最重的一场——**前面第 3、4、6.4、8.6 章任何一处不对，它都走不完**。

### 11.4 修掉的十六个缺陷（都是"看着能跑、其实不对"的那类）

1. **`groundBelow()` 语义错一层**。找到最近的 occupied 格后应当返回它上面那一格（站立格），旧代码又加了一层，于是所有"可站立"判定偏上一层。
2. **首次规划失败后永不重试**。原来是 `if (have_plan && …)`，第一次失败就锁死。改为 `t - last_plan_t > 1.5 || (have_plan && routeError > 0.45)`，失败也按时重试。
3. **单层俯仰只画出半径 2.16 m 的一个环，脚下没有点**。改 12 层 + 近场补点。
4. **起点格整列 UNKNOWN**。地板射线最近环在 0.65 m，近场补点只有 240 个，`(18,18)` 整列没点 → `plan fail: start not in grid`。修法：`stampPoint()` 对地面回波（z ∈ (−0.09, 0.06)）额外做 3×3 邻域稠密化。地面是连续平面，填洞不会藏住障碍——桌上的物体自己会有回波。
5. **`plan fail: goal not in grid`**。目标在 8–13 m，远超 4 m 感知。修法：`surveyMap()` 先验建图，每 2.4 m 一个站位各扫一帧（等价于"操作员先拿 Odin1 走一圈"）；`rebuild()` 先插实时点，再把先验里**所有已知状态**（不只 occupied，还有地板上方的 free）拷到仍然是 UNKNOWN 的格子上。少拷 free，可站立判定就全灭。
6. **每个 rollout 都判成压地**。`blocked2D` 从 z=0.1 起算，`(0.1 − (−0.5)) / 0.1` 浮点得 `5.999999999999999`，`floor` 落到地板层本身。改为 z=0.12 起、band 只到 0.42 m——只算躯干，桌面 0.75 m 不挡、桌腿挡。
7. **里程和最小净距严重偏低**（2.3 m vs 实际 11 m）。这两个量被塞在 `if (std::fmod(t, 0.10) < dt_sim*0.5)` 的采样分支里，而 t 每次加 0.02 永远落不到 0.10 边界。改为整数步计数（`step % 5` 采样、`step % 25` 建图），**计量每 tick 都做**，与采样解耦。
8. **只查中心点 → 躯干角压到门框**。`narrow_gate` 在 (6.68, 3.05) 撞墙，中心线却显示免费。改为包络 9 点采样（中心 + ±0.20 m 的四个方向）。
9. **绕行次数每控制周期加一次**（130 次）。改成状态机：偏离路线 > 0.30 m 记 1 次，回到 < 0.18 m 才退出。

膨胀半径同时从 3 格降到 2 格（0.20 m）。3 格 + 箱子会把 1.6 m 走廊彻底堵死，而真机能过——**过度保守和漏检一样是缺陷**，只是表现成"卡住"而不是"撞上"。

加多层这一场之后，又炸出七个。它们都不是调参能解决的，全是"判据用错了对象"：

10. **一格厚的面被判成浮空薄片**。`hasGroundSupport()` 的规则是"下方一格 free 即视为薄片"，用来防爬墙。但 0.10 m 楼板和 0.189 m 踏步本来就只有一格厚——于是整条跑梯、整块楼板在图上都站不住，**楼梯从来没有一次成功的 A\* 规划**（事件日志里 6.8 / 11.6 / 14.0 s 三次 `no path found`）。之前"能爬上去"是靠步态接管绕过规划。修法：同样一格厚，用地层宽度区分——墙每层只露一格，水平面在 5×5 邻域内占 8 格以上。`planner_sim` 七个用例的展开节点数一个没变（1228/559/97/1338/590/15529/15768），因为这个判据只影响本来就该放行的面。
11. **膨胀半径被算了两遍**。栅格已经按 0.17 m 半宽膨胀了 0.20 m，`blocked2D` 又套了一层 0.20 m 包络。0.70 m 的门洞于是只剩 `0.70 − 0.40 − 0.40 = −0.10 m` 可用宽度，里面没有一个合法格——**从几何上就过不去**，代价函数怎么调都没用。去掉包络、只判中心点（膨胀已经是包络），狗立刻能穿门。
12. **让行规则读的是出生位姿**。行人 `advance()` 改的是仿真内部副本，让行逻辑却遍历原始 `sc.obs`，看到的永远是 t=0 的 (9, 3)——所以它从不让行，直接撞上去。改为读推进后的副本，并只对"会动的"让行（静止承重柱要绕，不要停）。
13. **站立高度取自路径点**。路径记得整条梯段，于是身体从跑 A 顶端一步"抬"到二层楼板，跳过往返跑。更致命的是——A\* 在梯段上根本规划不出来（缺陷 10），路径为空，高度跟随直接失效。改为三个探针（脚下 −0.10 / +0.20 / +0.45 m）取不超过脚下 0.26 m 的最高真实面，逐级 0.02 m 抬升。**高度不再依赖规划是否成功**。
14. **分段到达判定被锁在"有计划"里**。`if (have_plan) { …if (dgoal < 0.45) 到达…}`——规划失败时 `have_plan = false`，狗站在自己落点旁 0.26 m 处整整 30 s 就是不推进。改为无条件判定（腿目标本身就是真值）。
15. **接管区少了高度维度**。楼梯步态接管区是纯 XY 判据，狗站上二层楼板后仍被判"还在跑 B 上"，而跑 B 的中线终点恰好就在它脚下——**它一直在追自己的中点**，原地缓慢打转直到超时。加高度上限（跑 A z<1.95、跑 B z<3.30），"梯段只在你还踩在梯段上时才算梯段"。
16. **转弯平台与跑 B 的交界被挡边封死**。平台加宽后，那条 0.08 m 的前缘挡边正好横在 y 1.74–1.82，也就是下楼通道口。删掉——平台东侧由外墙兜住，不需要再挡。

其中 11 是最值得记的一条：**"过度保守"和"漏检"是同一类缺陷**，前者表现成卡死、后者表现成撞击，但根因都是余量算错了对象。11.4 第 9 条那次把膨胀从 3 格降到 2 格，也是同一个道理。

### 11.7 这套仿真不证明什么

- **不证明 Go2 的步态能执行**。平地 DWA 出的 (vx, vy, wz) 在真机上要经 `stair_gait`/`sport_client` 落到 `1011`/`1049` 才动腿，这一段仍是开环待实测。
- **动态障碍的策略是"停等"而不是"绕行预测"**。仿真里行人匀速直线，真人不一定是；上面 5.5 s 的停等在真机上要配合声光提示，否则人不知道狗在让它。
- **点云是模型生成的**，玻璃穿透、反光、雨雾这些真实退化没有建模。第 8.5 节的挡边结论仍然成立，但那是靠现场实测得到的，不能从这套仿真里推。
- **没有里程计漂移**。仿真里位姿是真值，真机上 Odin1 的 SLAM 输出有漂移，`routeError > 0.45 m` 的触发频率会明显更高。
- **多层的 0.09 m 净距不能照搬**。仿真里步态接管只发 `wz` 做横向纠偏，靠 1.5 s 重规划把身体拉回中线；真机上 Go2 爬楼步态对 `linear.y`（侧向）的响应还没实测，若完全不走侧向，跑 B 段的余量会比这更小。第 8.5 节的挡边规格给了物理边界，但**横向闭环要不要发 `linear.y`，必须在真机上先测**。

### 11.8 楼梯段的局部动态避障：把梯段当"展开的平段"

前面十节里，梯段一直是**整段交给 `stair_gait` 盲走**的：`inFlight()` 命中就发常量前进，横向 `linear.y` 直接写 0。这在平地上没问题，但等于**梯段上没有动态避障能力**——踏面上站了人、堆了箱子，没有任何环节会响应，`collided` 只会事后告诉你撞了。

现在的规则（`test/nav_sim.cpp` 的 `stairTreadBlocked()`，与 mesh 页的 `stairLocalLeg()` 同一套判据）：

- **竖直不归局部层**：台阶级差由步态负责，所以踢面/踏面不进碰撞判据。这正是旧实现"任何候选都判碰撞、只能盲走"的根因——点集规划器把下一级踏面看成墙。
- **两侧边界是硬约束**：把梯段切成 `(s, t)` 走廊坐标系，`s` 沿跑梯向上、`t` 横向。单跑净宽 1.00 m，横向预算 `0.50 − 0.175 − 0.05 = 0.275 m`。**扶手、挡边、踏面本身都不算障碍**——它们就是走廊；只有人工放上去的杂物和会动的人才进判据（`Scenario::clutter`，等价于 mesh 页的 `state.obs`）。
- **高度与"即将站的踏面"比**，不是与 `base_z` 比：抬一级 +0.189 m、下一级 −0.189 m，只有落在 `+0.12 … +0.55` 带内的东西才算挡路。
- **判定是"能不能让开"，不是"有没有东西"**：把横向偏移挪到预算允许的最远处，剩下的横向间隙建模为实际间隙，`< r + 半机身 + 5 cm` 就停。

新增场景 `stair_tread_block` 把这层单独拎出来验：几何与 `stair_two_floor` 逐项相同，只在跑 A 第 6 级踏面上放一只纸箱。实测事件日志：

```
7.90 s  楼梯段局部层：踏面障碍 s=1.91 m、横向余量 0.00 m，停车等待
```

`横向余量 0.00` 是因为纸箱正压在中线（y 2.40）上——这是最坏情况。狗停在纸箱前约 1.9 m（前瞻 1.6 m + 箱体半径）不再前进，`collided = 0`、`mincl = 0.31 m`，超时 120 s 收场。**这是正确行为，不是失败**：1.0 m 净宽的跑梯扣掉 0.30 膨胀和 0.175 半机身之后横向只剩 0.275 m，比"0.22 m 的人 + 0.225 m 余量"小，物理上就没有绕过去的空间。要看到横向绕行，得把跑梯做宽到 ≥2 m——这是几何结论，不是调参。

同一套判据在 mesh 页面已有等价的实现与实测（`#single,ridge,treadblock`：无梯上障碍时可通行，梯上立柱时在 prog 2.2–3.4 m 停、4.0 m 起通行）。两个仿真器现在说的是同一件事。

**回放页**：`docs/multifloor/sim/nav_sim.html` 现在 6 场 × 2 规划器共 12 个场景卡片。`stair_tread_block` 的徽标是**按设计停车**而不是**未到达**：`reached = false` 说的是“没走完”，`held` 说的是“该停的地方停住了”，两者不能混着看。事件栏会直接打出上面那条停车记录。
