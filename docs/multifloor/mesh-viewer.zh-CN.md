# 点云转 mesh 实体视图

把仿真里扫描到的点云抽成表面网格，再用实体面渲染出来的离线页面。
配套点云视图是 [`sim/nav_sim.html`](sim/nav_sim.html)，本页是 [`sim/mesh_viewer.html`](sim/mesh_viewer.html)。

## 1. 为什么要单独做一版

点云视图回答的是「雷达扫到了哪些点」，mesh 视图回答的是「这层楼长什么样」。
同一份数据，两种读法解决两个不同的问题：

| | 点云视图 `nav_sim.html` | mesh 视图 `mesh_viewer.html` |
|---|---|---|
| 几何形态 | 每帧的点集，按播放头累积 | 对累积点做体素占据，只保留外表面 |
| 四层场景规模 | 终帧 16.1 万点 | 4.9 万顶点 / 9.9 万三角面 |
| 观感 | 有体积感，但墙和地板糊在一起，读不出门洞 | 地板、墙、门洞各有明确的面，能读出房间拓扑 |
| 透明度 | 点本身无法设置 | 8%–100% 可调，半透可穿墙看内部 |
| 主要用途 | 验证扫描覆盖、行人/障碍出现时机 | 验证建图质量、给上层提供碰撞体参考 |

## 2. 生成链路

脚本 [`test/build_mesh_scene.py`](../ros_ws/src/octo_planner_ros1/test/build_mesh_scene.py)，
一次跑完 5 个场景 × 4 档进度：

1. 读 `nav_sim_data.json`，按 `name` 去掉 ` · NeuPAN` / ` · DWA` 后缀去重 → 5 个场景。
2. 每档取「时间 ≤ frac × 总时长」的所有扫描帧，把这批帧的点拼成累积点集。
3. 体素占据：`idx = floor((p − [wx0, wy0, z0]) / VOX) + 1`，每格只要有 1 个点就算占据。
4. 闭运算 `binary_closing(3×3×3)` 补一格缝，避免点云稀疏处碎成孤岛。
5. 六邻接面剔除：只保留「邻居为空」的那一面，被邻格挡住的内部面全部丢掉。
6. 顶点按角点 key 合并，相邻面共享顶点；法线由 `computeVertexNormals()` 生成，再按 `normal.y` 分三档顶点色（朝上=地板、朝下=底面、其余=墙）。
7. 打包：顶点为 int16 ×3、索引按顶点数自适应 `uint16` / `uint32`，两者 base64 后内联进页面。

关键参数：

| 参数 | 取值 | 依据 |
|---|---|---|
| 体素边长 `VOX` | 0.12 m | 相对 0.52×0.34 m 机身足够细；降到 0.07 m 时总文件从 7.4 MB 涨到 68.9 MB，不可用 |
| 档位 `STEPS` | 0.25 / 0.5 / 0.75 / 1.0 | 档数越多过渡越顺，但体积线性增长 |
| 闭运算核 | 3×3×3 全 1 | 只补一格，再大就会把门洞糊死 |
| 索引类型 | uint16 / uint32 自适应 | 四层场景 49366 顶点仍在 uint16 范围，省一半索引体积 |

## 4. 机器狗与局部规划器窗口

页面上除了建筑，还有两样东西是专门用来读规划的：

**机器狗** 是程序化拼出来的，不是加载 URDF 的 DAE 网格 —— 那套美术模型 20 MB，只为表达 0.7 m 的形体不划算。
尺寸按 `go2_description` 的比例：整体 0.70 × 0.31 × 0.40 m，躯干 0.42 × 0.20 × 0.10 m 坐在离地 0.30 m 处，四条腿各两段（大腿 0.05、小腿 0.035 截面），背部有一个 Odin1 盒子和两盏青色头灯。
脚底就是 z = 0，和 `trace` 里 `z = 0` 对齐，不额外抬高。

**局部规划器窗口** 是 2 m 半径的圆盘，跟着机器人走：

| 图层 | 颜色 | 含义 |
|---|---|---|
| 圆环 | 青 | 规划器允许使用的范围，中心是采样时刻的位姿 |
| 实心格 | 红 | 传感器真正扫到、判为 occupied 的格子 |
| 半透格 | 橙 | 只因为两格膨胀才变实心的格子（`inflate(2)`，0.20 m） |
| 点阵 | 灰 | 狗身高度带（base+0.24…0.44 m）内从未观测到的格子 |

三层必须分开画，否则看不出「哪里真有东西、哪里只是安全边界、哪里根本没看过」。
仿真里每 0.3 s 采一次窗口（step % 15），所以 5 个场景分别是 70 / 101 / 82 / 145 / 500 帧。

两个实现细节值得记：

- 圆盘放在**采样时刻的中心** `(cx, cy)`，不是狗的实时位置。格子存的是相对窗口角的偏移，
  两者混用会让图案在狗移动时滑出圆环。
- 格子尺寸 0.10 m，是规划器真实的分辨率，不是画得粗。

## 5. 页面怎么用

- **场景**：5 个按钮，切换会重置进度到 100%。
- **透明度**：滑块 8–100%，预设三档 —— 实体 100 / 半透 45 / 透视 15。
  低于 99% 时材质不写深度缓冲（写深度会让背面被前面剔掉，壳看起来会消失）。
- **进度**：0–100%，配「播放 / 复位」。复位把进度回 0，只留起点那一档的网格。
- **视角**：左键拖拽旋转、滚轮缩放、右键平移、「视角复位」回到默认斜俯视。
  相机按 **Z 轴朝上**（数据是 ROS 约定），不是 three 默认的 Y 朝上。
- **机器人**：绿方块 0.52×0.34×0.30 m + 前方黄色锥体表示朝向。
  方块中心还有一颗**穿墙绿点**（关掉深度测试），四层叠在一起时也能定位狗在哪层。
- **全局路径**：亮青线，同样穿墙显示，半透模式下能看到整条跨层路线。
- **局部窗口 / 跟随狗**：两个开关。跟随狗会把相机中心锁到机器人身上，方便进楼看细节。
- **URL 直达**：`mesh_viewer.html#3,30` → 第 4 个场景 `stair_two_floor` + 透明度 30%；
  再往后加两个参数可以定进度和机位：`#0,100,55,2.6,1` = office、实体、55% 进度、相机距离 2.6 m、跟随狗。

## 6. 已知局限

1. **只有扫到的方向有面**。没扫到的一侧是空的，看到的是「壳」不是封闭体，
   不能直接当 watertight 碰撞体喂给物理引擎。
2. **0.12 m 体素吃细节**。15 cm 踏步约 1.25 格，台阶能看出来但级数会被抹平；
   楼梯语义判断仍以点云和规划器那份为准。
3. **4 档跳变，不是逐帧**。进度条连续走，网格只在 4 个档位重建（每档都是全量累积点重算）。
4. **不是真值几何**。这是点云反推的表面，比设计图纸上的墙厚约 1 个体素，边角也会缺。
5. **半透不写深度**。通透好看，但两个壳叠在一起时混合顺序由 GPU 决定，局部会偏亮或偏暗。
6. **窗口是 0.3 s 采样**。原先 0.5 s 一帧，按 0.28 m/s 走的行人两帧之间挪了 0.14 m（超过一整格），膨胀环被画成落后半步；现在 0.3 s 一帧，圆盘中心还在相邻两帧之间做线性插值，格子内容取最近帧。
7. **窗口是二维的**。采样时只看 `base_z + 0.24 … + 0.44 m` 这一段高度带，楼梯踏步上方会判成空的。
8. **膨胀图只对应 DWA 那张栅格**。NeuPAN 在仿真里用的是点集硬约束（< 0.22 m），不是这张膨胀图；
   所以橙色那圈对 NeuPAN 只是参考，不是它真正的判据。
9. **橙色环会有缺口，来源有四种**：① 窗口是圆，边界外不采样；② 点云稀疏处墙本身就有洞，
   膨胀跟着有洞；③ 楼梯区（`inStair`）的膨胀被主动清掉，否则 0.30 m 踏步加上两侧 0.20 m
   膨胀只剩中间一格，`stair_gait` 根本进不去楼梯；④ 未观测格——它是灰点阵，不是空地。
   圆内逐格核对：office 82.5%、corridor 88.8%、narrow 69.9%、stair 54.1%、four 61.1%
   的「应有膨胀」被标上了，缺口全部落在这四类里。
10. **`inflate(2, 0, skip_standing_surfaces)` 的取舍**。跳过「上方是自由空间的占据格」是为了不让
    地板和台面自己生出膨胀；但它同时也跳过了矮障碍的顶面。把这层跳过关掉（`NAVSIM_SKIP_SURFACES`
    不设）会让 1.2 m 窄门的膨胀把门洞吃掉，NeuPAN 在 13.4 s 被对向行人撞上（实测，DWA 不受影响）。
    所以现在保留跳过：宁可橙环在矮障碍那边薄一点，也不让窄门场景失效。
11. **膨胀每 0.3 s 随地图重建**（`deinflate` + `inflate`）。原先只在建图时做一次，而 `scan()` 会把
    真实观测写回已被膨胀改色的格子（它只跳过仍然是 `kFree` 的格），墙边那圈于是被观测一格一格擦回去。
12. **三角化怎么做的，以及楼梯为什么是几何**。点云按 0.12 m 体素化，先做各向异性闭合（(3,3,1) 与 (1,1,3) 各两轮）补扫描环之间的缝，再按列剪掉「浮在一格以上、长度不超过两格」的孤立碎片——那是射线擦过栏板落在踏板上方的回波。楼梯的踏板面**不是**扫描出来的：站在踏板上，脚下的面在传感器视场外，两级之间的踢面又背对传感器，所以实拍只剩栏板和碎块。仿真里每一级都有一块同高的栏板，踏板的高度和 x 跨度直接从它反推，宽度按梯段宽补——这和真机上 `seed_stair_prior` 拿模型先验是同一件事，不是凭空画。
13. **视角可以用链接指定**。`#场景,透明度,进度,距离,跟随,yaw,pitch`，例如 `#3,45,100,7,0,-2.4,0.75` 会直接落进两层楼梯的梯井，不必手动转到墙外再往里看。
14. **每级是「踏板面 + 踢面」一整块，不是一块薄板**。踏板本身只有 0.12 m 厚，而级高 0.19 m，两级的板之间只剩 7 cm 的缝——体素化后要么贴死、要么看起来像一段斜坡。所以反推出的每一级都往下延伸到下一级的顶面，构成 0.30 × 0.19 的实心台阶块，台阶的棱线才回得来。踏板是几何先验里唯一「本来就精确」的东西，所以它在所有形态学操作之后才写入，不会被闭运算熔成一段斜面。
15. **「只看楼梯」按钮**。楼梯间四面都是墙，全模型看的时候台阶总被挡住。该按钮只画三角形重心落在楼梯区间内的面（链接里可用第八个参数：`#3,100,100,6.5,0,-2.4,0.5,1`），相机同时移到梯井中心。
16. **mesh 页一次加载全量点云**。早前为了看出「扫描在长出来」，几何按 25/50/75/100% 分了四档；结果是切场景时会看到模型重新长一遍。现在只留 100% 一帧，数据从 10.3 MB 降到 4.3 MB，打开即是完整模型。
17. **楼梯区间内只保留几何，不保留扫描残块**。清空楼梯核心区间后按已知结构重建：踏板（每级从栏板反推）、栏板本身、以及每段梯段顶端的平台（每层一块）。代价是该区间内扫描到的墙、柱、门也不再出现在 mesh 里——那里现在是"楼梯模型"，不是"成像"。这是取舍，不是修复。


## 7. 复现

```bash
cd ros_ws/src/octo_planner_ros1
python3 test/build_mesh_scene.py     # → docs/multifloor/sim/mesh_scene_data.json

cd docs/multifloor/sim
python3 - <<'PY'
s = open("mesh_viewer.template.html").read()
s = s.replace("/*__THREE__*/", open("three.min.js").read())
s = s.replace("/*__DATA__*/", open("mesh_scene_data.json").read())
open("mesh_viewer.html", "w").write(s)
PY
```

要求 `numpy` + `scipy`（`scipy.ndimage.binary_closing`）。无需 `trimesh` / `open3d`。

## 8. 想更进一步的话

- 导出 OBJ / GLB 给 Isaac Sim 或 MuJoCo 当静态碰撞体（要先补成封闭网格）。
- 用 marching cubes 代替方块面，出光滑表面（体积会涨，但可以降到 2 档）。
- 每层单独切片渲染，而不是靠透明度看内部。
- 档位从 4 提到 8，过渡更顺，体积 ×2。
